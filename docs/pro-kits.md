# Hosted Font Awesome Pro Kits

Hosted Pro is an opt-in integration for an existing Font Awesome subscription. Automatic Font Awesome Free remains the default. BFA does not sell Pro access, manage billing or change a Font Awesome account.

## Connect and use

In Font Awesome, publish a v7 Pro **By Style** Kit, select **Web Fonts** and **CSS-only** embedding, and enable compatibility. Include Classic Solid, Regular and Brands. Classic Light and Thin are optional. Additional families, custom icons, By Icon Kits, SVG delivery and older versions are unsupported. Configure permitted domains in Font Awesome, including your staging domain. Keep the version on Latest 7.x or a specific v7 release.

In Settings > Better Font Awesome, choose **Hosted Pro kit** in the first **Font Awesome source** dropdown. **Local Free (no CDN)** identifies the bundled-local option. API Key and Kit use the same label/control rows as the other settings. If switching from Local Free, save settings first to turn off local delivery before making account requests:

1. Enter an [account API token](https://fontawesome.com/account#api-tokens) with **Read Kits Data** permission in the password field. Use HTTPS for the WordPress administrator connection. The minimum scopes remain `public` and `kits_read`; SVG, download, account profile, domain and billing scopes are unnecessary.
2. Click **Connect account**. Inline loading and failure messages appear beside the triggering control without changing the active connection. This authorizes the account and lists Kit names/configurations, without acquiring icon catalogs or activating a Kit.
3. Choose a kit from the dropdown to start connecting it immediately. Duplicate or missing names include an identifier. Unsupported Kits show an explanation and do not connect. Loading or refreshing the list never selects a Kit, even if only one exists. The selected Kit is checked again under the current authorization before catalog acquisition and activation.

After successful discovery, **API token saved** replaces the password entry. **Update token** opens an empty password field; **Cancel** discards the edit. **Refresh kits** reuses saved authorization to refresh names/configurations without fetching catalogs. A failed replacement token/list request leaves saved authorization and the active Kit intact. The saved token is never returned to the browser. The active Kit retains its own credential until a replacement finishes activation. **Refresh active kit** refreshes that Kit's configuration/catalog using its credential, independently of account discovery. Update, delete and refresh actions use icon-and-text links. The connected Kit remains selected and is marked "(active)" in the native dropdown, including after a Kit-list refresh. The "Choose a kit" placeholder is disabled while connected. Selecting or restoring that displayed value programmatically never starts acquisition. The successful connection announcement remains available to screen readers without repeating the Kit name beside the dropdown. The **Kit details** toggle sits inline with the dropdown and actions. It opens a compact label/value panel for icons, technology, version, older-version compatibility and Classic styles, using saved metadata without HTTP. Older discovery lists reuse the active snapshot when available, otherwise retain their text summary until the next explicit list refresh; a concise unsupported-kit explanation and errors stay visible. Unsupported kits expose the same details panel, showing reported configuration and the full requirements without implying support. Symbolic versions include the major and resolved release, for example **v5 latest (5.15.4)** or **v7 latest (7.3.1)**. The major for the legacy latest value comes from the API's resolved release, never an assumption; unavailable release metadata leaves the reported selection unchanged. Previously saved unsupported summaries remain available inside the panel until **Refresh kits** updates their structured display data. Secondary action links underline their text only. Refresh of the active catalog appears only when a saved Kit exists. Source labels replace routine delivery guidance; actionable conflicts and the save requirement when leaving Local Free remain visible. **Disconnect kit** appears inside the expanded details for the connected kit, keeping the main action row compact. It removes that connection, catalog and pending work, retains encrypted account authorization and the available kit list, and returns hosted delivery to Automatic Free. Selecting a kit again reconnects with the saved token. Previously chosen Local Free remains local. **Delete token** asks for confirmation because it additionally removes account authorization and the kit list.

The selected configuration summary is a metadata check, not a delivery guarantee. BFA constructs the CSS-only embed URL as `https://kit.fontawesome.com/KIT_ID.css` from the validated Kit identity. Manual identifiers and CSS URLs are not part of normal setup. API fields do not verify permitted browser domains, font loading, or future subscription entitlement; those remain delivery acceptance checks.

Selecting a supported kit starts validation immediately. The selector is disabled during preparation to prevent overlapping selection requests. A failed attempt offers **Retry connection** or another selection; the working connection remains intact. The settings page continues preparation in bounded asynchronous steps and shows the current task: loading icons, checking compatibility, then verifying the Kit. API page counts are not shown as connection progress. Keep it open until activation finishes; reloading resumes pending work. Initial connection does not require WP-Cron. Preparation retains the working Free or previous Pro configuration until a complete candidate passes validation. Refresh active kit uses the same immediate flow, and scheduled daily refresh uses the same acquisition code. The picker catalog uses the API maximum of 500 icon/style variants per page, grouping up to 32 pages into one GraphQL request. A catalog of up to 16,000 variants needs one catalog request; larger catalogs continue in bounded groups. Free compatibility and final Kit revision checks still run before activation. Each request retains the 10-second timeout and 4 MiB response limit. Incomplete pages, duplicate identities or inconsistent counts reject the entire group without saving partial results. Existing pending connections resume at their saved page. Ordinary page/editor loads reuse the saved catalog. CSS and fonts are not downloaded by this preparation. Connected is shown only after a new request confirms effective Kit delivery under BFA ownership. An initialization filter that prevents that selection is reported as an ownership/configuration conflict. Reopen editors after activation to obtain the new catalog.

Pick an icon by name and choose an available Style. Classic/hybrid pickers insert the existing shortcode. The native block retains its existing name/style attributes and dynamic renderer. Site default can use the available Classic styles; Brands is an icon-specific style, not a site default. An omitted native block style remains Solid; omitted shortcode styles keep their established legacy `fa` markup. Explicit saved choices remain explicit even when unavailable. Inherited icons try the requested default, Solid, Regular, Brands, Light, then Thin. Missing names retain the requested style. These rules do not rewrite content.

## Delivery, failures and switching

A connected Kit is **hosted delivery**, separate from bundled-local Free. Browsers load CSS from `kit.fontawesome.com` and imported CSS/fonts from Font Awesome's delivery hosts, including `ka-p.fontawesome.com`. These requests disclose ordinary connection information to the vendor and may be subject to domain restrictions, subscription conditions and Kit usage limits. No Font Awesome JavaScript loader is used. BFA does not download, mirror or distribute Pro assets. TinyMCE receives a direct CSS URL through `mce_css`; remote theme-editor imports are not installed.

Changing the source dropdown previews relevant settings without activating assets or making metadata requests. **Save Settings** applies Automatic Free or Local Free and pauses Pro preparation/refresh while preserving saved authorization and the active snapshot. Local Free loads no Pro assets or metadata. Selecting Hosted Pro kit does not activate it: select a Kit or use **Refresh active kit** to validate and activate the connection. Switching delivery reloads the page after saving so BFAL's immutable choice applies on the next request. Hidden Free version/shim controls retain their values. Disconnecting only the kit preserves account authorization and choices, but gives them a fresh selection generation so old selections, workers and discovery responses cannot restore the connection. Deleting the token forgets account authorization, Kit choices, credentials, catalog and pending work. None of these actions changes saved content: unavailable Pro icons may become blank. A failed or incomplete replacement keeps the old active snapshot.

Temporary service failures retain last-known-good metadata and retry at bounded intervals, stopping after five failed requests in one preparation attempt. An existing active Kit gets another scheduled recovery opportunity after a day; an initial failed connection needs Retry connection or a new Kit selection. Authorization failures, unsupported configuration, incomplete catalogs and revision changes stop preparation with an actionable status; Retry, a new selection or Refresh starts again. Interrupted steps have an expiring lease. Old or canceled work cannot promote a candidate or recreate a canceled event.

Cached metadata is neither proof of current entitlement nor a guarantee of hosted font availability. Blocked or unavailable CSS/fonts can leave blank glyphs; there is no silent Free replacement or authentication retry during rendering. External edits to a hosted kit take effect independently of BFA. A local metadata snapshot cannot roll back those remote edits.

## Ownership and local state

BFA captures whether its existing first BFAL initialization actually ran. An earlier owner remains authoritative even if its Kit URL matches. BFA installs its Pro catalog only when that ownership and the effective Kit assets match. The Free metadata getters retain their Free meaning. BFAL receives only the immutable delivery mode, validated CSS URL and 7.x channel, never credentials or a Pro release manifest.

Deactivation cancels pending Pro work while retaining the saved delivery choice for explicit reactivation. Network activation/deactivation applies only to the current network. Workers do not reuse credentials after switching to a different site.

Pro account authorization/Kit choices, credentials, candidate and active metadata use a separate per-site, non-autoloaded WordPress option. Icon identities are stored compactly and converted to the existing picker records on demand. AES-256-GCM encrypts tokens using site-specific material derived from WordPress authentication keys/salts in wp-config.php. OpenSSL and configured AUTH_KEY/AUTH_SALT constants of at least 32 characters each are required for connecting; there is no plaintext fallback. Salt changes require reconnection. Encryption protects a database-only disclosure, not a compromised WordPress runtime. Secrets are never included in editor configuration, status responses or BFA diagnostics. Administrators need `manage_options` and a valid nonce for connection operations. WordPress editing permission does not itself confer a Font Awesome license.

Explicit account connection or Kit-list refresh makes two bounded server requests: token exchange and a fixed `me.kits` configuration query. It requests names, identities, version/revision, delivery/subset/compatibility settings and style counts, never icon catalogs, account profile or domain lists. The official API exposes `Account.kits` as an unpaginated list. Full icon catalog pagination remains in the existing Connect flow. A malformed or truncated list fails as a whole. Style inventories outside the existing bounded eligibility checks remain unsupported. Discovery uses a separate generation and an atomic comparison so older responses cannot overwrite newer authorization or disconnects. Browser input changes also invalidate pending results. Connect requires membership in the current successful list and its generation, then reauthorizes and repeats the existing selected-Kit validation.

Family-style counts come from `iconVariantsPaginated(pageSize:1).totalIconVariantCount` without selecting icon records. `FamilyStyleSubset.only` is null for a whole included style and must not be used as its count source.

Beyond explicit account connection and Kit-list refresh, only Connect/Refresh batches and scheduled Pro work contact the fixed Font Awesome API. Each acquisition batch performs one bounded request with a timeout, TLS verification, no redirects and a response-size limit. Kit-scoped pagination checks counts, unique identities, selected styles and revision consistency. Same-release Free metadata enriches labels/aliases and checks coverage; the current local Free catalog provides an additional compatibility floor. Ordinary frontend, admin, editor, picker and getter requests read local data only. Free acquisition, records and retry behavior remain unchanged. Its activation guard also skips scheduling when a saved Pro connection will own delivery.

## Verification and publication gates

Synthetic tests exercise state transitions, ownership, security, inheritance and editor loading. Acquisition checks cover a full-sized catalog in one request, catalogs beyond the 32-page group boundary, resuming older page checkpoints, and rejection of missing, misnumbered or duplicate pages without partial persistence. On the QA site, verify selection and Refresh finish with WP-Cron disabled and preserve the active connection after a failed group. Browser fixtures may use a full-sized synthetic catalog and a publicly distributed Free font to test transport; these are not real Pro delivery acceptance. A securely supplied non-production Kit must still validate actual delivery and supported styles before publication.

The integration may temporarily pin an exact reviewed BFAL development commit. This is not a stable dependency adoption. Before publication, adopt its reviewed public stable release, restore exact stable dependency assertions and pass strict Composer validation and release-tree identity checks without development-pin exceptions. Keep full package QA, WordPress-floor editor acceptance and owner approval as release gates. No new BFA version or publication is implied by this feature branch.

An older BFAL dependency is a Free emergency compatibility path, not supported Pro delivery.
